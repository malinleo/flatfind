# Агрегатор аренды в Тбилиси — спека MVP

Nov 18, 2026 · @Leonid

MVP — агрегатор долгосрочной аренды квартир в Тбилиси: собирает объявления из нескольких источников, склеивает дубли с помощью AI и сразу шлёт новые совпадения в Telegram. Пет-проект, пользователей мало, главное — скорость уведомлений и чистая выдача без дублей.

## 1. Бизнес-требования (что делаем в MVP)

### 1.1 Сбор объявлений

- Источники на старте: ss.ge, myhome.ge и список Telegram-групп (точный состав определяется при подключении). Обход регулярный, интервал задаётся на источник (ориентир 5–15 минут).
- Объявление, которое уже видели в этом источнике (тот же `source + external_id`) и которое не изменилось, повторно не обрабатывается — обновляется только «последний раз видели».
- Если у объявления поменялся текст или цена, оно обрабатывается заново.

### 1.2 Извлечение данных и фильтрация

- Каждое новое или изменённое объявление проходит через недорогую LLM и превращается в стандартизированный JSON по полям манифеста.
- Если источник сам отдаёт структурированные поля (цена, площадь, этаж), берём их напрямую, LLM только дополняет пропуски.
- LLM определяет тип объявления: сдаю / сниму / подселение / продажа / спам / другое. Всё, кроме «сдаю», получает статус `rejected`.
- Обязательные поля: цена, валюта, район. Нет хотя бы одного — `rejected`.
- Полнота считается формулой по весам полей из манифеста, не LLM: `poor` → reject, `medium` и `rich` → accept.
- Посуточная аренда в MVP не собирается: такие объявления получают статус rejected.
- От отклонённых объявлений остаётся короткая запись (`source`, `external_id`, `content_hash`, причина) с TTL 6 недель — чтобы при следующем обходе не платить за них LLM снова. Первые недели храним и сырой текст для отладки промпта.

### 1.3 Дедупликация

- Каждое объявление хранится отдельной записью с источником и ссылкой. Дубли привязываются к одной «квартире» (кластеру), чтобы в карточке были видны все источники.
- Без AI склеиваются только объявления с одинаковым нормализованным текстом (совпал хеш).
- Всё остальное: дешёвый подбор кандидатов, затем решение принимает LLM.
- Источники кандидатов: похожий текст (триграммы), похожий смысл (эмбеддинги, работают между русским, английским и грузинским), совпадение параметров (район + комнаты + цена ±15% + площадь ±10%), тот же контакт.
- Совпадение контакта само по себе ничего не склеивает, оно только добавляет кандидата для LLM.
- Вердикт LLM: `same` / `same_building_different_unit` / `different`.
- Картинки в MVP не сравниваются.
- Если у той же квартиры изменилась цена, это событие «цена изменилась» и запись в историю цен, а не новое объявление.
- Квартира, которая снова появилась после неактивности, привязывается к старому кластеру и даёт событие «снова сдаётся».

### 1.4 Контакты

- Телефон, email и аккаунт автора в источнике нормализуются и хранятся как отдельная сущность «контакт», со счётчиком объявлений.
- В MVP контакты только собираются и используются как источник кандидатов. Признак «агент» и фильтр по нему — в будущих фичах.

### 1.5 Поиск, лента и карточка

- Поиск идёт только по активным квартирам (кластерам), не по отдельным объявлениям.
- Фильтры — это поля манифеста с пометкой «в поиске». Нет поддержки поля в поиске — проект не собирается.
- Карта: результаты на карте, фильтр «в радиусе X км от точки».
- Сортировка: по свежести (по умолчанию) и по цене. Полнота на сортировку не влияет, есть фильтр «только подробные».
- Лента событий: новые квартиры, снижение цены, «снова сдаётся».
- Карточка квартиры: основные поля, все источники со ссылками, история цены, «впервые замечено N дней назад», фото по ссылкам из источников (у себя не храним).
- Квартира становится неактивной, если ни одно её объявление не видели 3 дня или источник показал, что объявление снято.

### 1.6 Пользователи и уведомления

- Сайт работает без входа: поиск, лента и карточки открыты всем.
- Подписки и уведомления живут только в Telegram-боте. На сайте кнопка «Подписаться в Telegram» сохраняет текущие фильтры и открывает бота по ссылке с параметром start; после нажатия Start подписка создана. В боте же список подписок, пауза и удаление.
- Уведомления только по событиям: новая квартира, снижение цены, снова сдаётся. Каждое событие по одной квартире приходит пользователю один раз.
- Уведомление уходит сразу после дедупликации. Периодических повторов «всё ещё сдаётся» нет.

## 2. Технические требования

### 2.1 Стек

| Слой | Выбор | Зачем |
| --- | --- | --- |
| Бэкенд | Go, один репозиторий, один бинарник с ролями `api`, `worker`, `bot` | модульный монолит, простой деплой |
| База | PostgreSQL + PostGIS, pgvector, pg\_trgm | одна база на всё: данные, гео, эмбеддинги, нечёткий текст |
| Очередь | River (очередь задач поверх Postgres) | без Redis и брокера; задача ставится в одной транзакции с данными, так что outbox получается сам собой |
| Доступ к базе | sqlc + goose (миграции) | типизированный Go-код из обычного SQL, без ORM |
| Парсинг сайтов | net/http + goquery для ss.ge и myhome.ge | для начала хватит HTML; если у сайта есть внутренний JSON API, лучше брать его |
| Парсинг Telegram-групп | MTProto-клиент gotd/td от отдельного аккаунта Telegram | веб-превью `t.me/s/…` есть только у публичных каналов, а бот не читает группы, куда его не добавили; аккаунт заводить на отдельный номер — его могут заблокировать |
| LLM | провайдер за интерфейсом: Gemini через Vertex AI или OpenAI, выбор позже; дешёвая модель со structured output; мультиязычные эмбеддинги | модель меняется без переписывания кода; Vertex AI авторизуется сервисным аккаунтом GCP без отдельных ключей |
| Курсы валют | официальный курс НБГ, раз в день | цена в USD для поиска и сравнения |
| Фронт | Vite + React + TypeScript + shadcn/ui + TanStack Query + TanStack Router | см. ниже |
| Карта | MapLibre GL (react-map-gl) с OSM-тайлами | бесплатно, без ключей Google |
| Контракт API | OpenAPI-спека → oapi-codegen (Go) и openapi-typescript (TS) | типы фронта и бэка из одного источника |
| Бот | Telegram Bot API, long polling; deep link со `start`-параметром для подписки с сайта | единственный канал подписок и уведомлений, без вебхуков |
| Деплой | GCP: одна VM Compute Engine + docker compose (Postgres с расширениями, приложение, Caddy для HTTPS и статики фронта); ежедневный `pg_dump` в Cloud Storage | минимум инфраструктуры и счетов; Cloud SQL — вариант позже, если захочется управляемую базу (сначала проверить, что там есть все три расширения) |

**Почему не Next.js.** Бэкенд уже на Go, а Next добавляет второй сервер со своими концепциями: SSR, server components, своё кэширование. Для новичка это два бэкенда вместо одного, а SEO здесь не нужно. Vite + React — тот же React и тот же shadcn/ui, но сборка — просто статика, а все данные идут из Go API. Альтернатива с минимумом JS — templ + htmx прямо в Go, но тогда React выучить не получится.

### 2.2 Архитектура

- Модульный монолит. Модули: `ingestion` (обход источников), `enrichment` (LLM-извлечение, эмбеддинги), `dedup`, `catalog` (поиск и read-модель), `notifications`, `identity` (пользователи).
- У каждого модуля свои таблицы и Go-пакет. Чужие таблицы напрямую не пишем, модули общаются доменными событиями через задачи River.
- CQRS без фанатизма: сторона записи — объявления, рёбра, кластеры; сторона чтения — денормализованная таблица `apartment_view`. Её обновляет проектор по событиям. База одна, но поменять хранилище для чтения можно без трогания стороны записи.
- DDD: главный агрегат — «Квартира» (кластер): решает, какое объявление к ней привязать, и порождает события `apartment_listed`, `price_changed`, `relisted`, `deactivated`, `merged`.

### 2.3 Пайплайн

&#91;embedded content: пайплайн обработки объявления · 3 ранних выхода\]

Три ранних выхода отсекают повторы, точные копии и мусор, поэтому до LLM-судьи доходит малая доля всего, что приносит обход.

1. `crawl_source` по расписанию. Для каждого объявления — upsert по `(source_id, external_id)`. Если `content_hash` не изменился, обновляется только `last_seen_at`.
2. Новое или изменённое объявление: нормализуем текст (нижний регистр, без эмодзи, пунктуации и лишних пробелов) и считаем `text_hash`. Совпал с принятым объявлением — привязываем к его кластеру. Совпал с отклонённым — сразу `rejected`. LLM в обоих случаях не вызываем.
3. `extract`: LLM с JSON Schema из манифеста → поля, тип, контакты. Дальше расчёт полноты и либо `rejected`, либо принято.
4. `embed`: эмбеддинг от собранного текста «район, улица, комнаты, площадь, этаж + описание».
5. `dedup`: подбор кандидатов (2.5) → один вызов LLM-судьи → рёбра → назначение кластера.
6. События кластера → `project_view` (обновить `apartment_view`) и `match_subscriptions` → `send_telegram`.

Если LLM-судья не ответил за 2 минуты (с ретраями), объявление становится новой квартирой с флагом `needs_recheck`. Позже фоновая задача прогоняет его через дедупликацию ещё раз и, если нужно, сливает. Скорость уведомления важнее редкого дубля.

#### Как работают рёбра

Ребро — это запись в `match_edge` о решении по паре объявлений: «одна квартира», «тот же дом, другая квартира» или «разные». Источник правды — рёбра, а `posting.cluster_id` — всего лишь сохранённый результат. Кластер = связная компонента графа по рёбрам `same`.

Зачем так, а не просто `cluster_id`:

- **Объяснимость.** Видно, почему два объявления склеены: метод, уверенность, причины от LLM.
- **Кэш.** Пара, по которой уже есть решение (в том числе «разные»), во второй раз в LLM не уходит.
- **Разделение.** Ошибочную склейку исправляем, перевернув одно ребро в `different` (`method = manual`) и пересчитав компоненты внутри этого кластера — это BFS по нескольким десяткам узлов в Go.

Пример: A–B `same` (тот же текст), B–C `same` (LLM, 0.9), C–D `different`. Получается кластер {A, B, C}, D отдельно. Если потом выяснится, что B–C — ошибка, переворачиваем ребро и получаем {A, B} и {C}.

Правила назначения кластера после судьи:

1. Нет ни одного `same` с уверенностью ≥ 0.8 — новая квартира.
2. Все `same` указывают на один кластер — присоединяемся к нему.
3. `same` указывают на два разных кластера — сливаем, только если оба ребра ≥ 0.9. Иначе присоединяемся к самому уверенному и пишем в лог конфликт.
4. При слиянии выживает старший кластер (ссылки на него не ломаются). Младший получает `status = merged` и `merged_into`, его URL редиректит.
5. Рёбра `same_building_different_unit` и `different` хранятся как отрицательные и ничего не склеивают.

### 2.5 Дедупликация: кандидаты и судья

Кандидаты ищутся среди принятых объявлений за последние 60 дней, четырьмя SQL-запросами:

| Источник | Как | Индекс |
| --- | --- | --- |
| похожий текст | `similarity(norm_text) > 0.5`, top 10 | GIN pg\_trgm |
| похожий смысл | косинусная близость эмбеддинга, top 10 | HNSW pgvector |
| параметры | тот же район и комнаты, цена ±15%, площадь ±10% | btree `(district, rooms, price_usd)` |
| контакт | общий `contact_id` | btree на `posting_contact` |

- Результаты объединяются и схлопываются до кластеров: от каждого кластера берём одно самое полное объявление.
- Пары, по которым уже есть ребро, пропускаются.
- Кандидаты ранжируются по числу сработавших источников, в судью уходят максимум 5. Нет кандидатов — сразу новая квартира, без LLM.
- Судья — один вызов на новое объявление: его JSON + текст (обрезанный до \~1500 символов) и то же для каждого кандидата. Ответ — массив `{candidate_id, verdict, confidence, reasons}`, temperature 0.
- Правила в промпте: цена может отличаться; другой этаж или несовместимые площадь / комнаты — не `same`; тот же адрес, но разные параметры — `same_building_different_unit`; сомнение — `different`. Лучше пропустить дубль, чем склеить две разные квартиры.

### 2.6 Манифест полей

- Один файл `fields.yaml`. У каждого поля: имя, тип, единицы, значения enum, `required`, вес для полноты, оператор поиска (range / enum / bool / geo / none), показ в карточке, подсказка для LLM.
- `go generate` делает из него: JSON Schema и часть промпта для извлечения; миграцию колонок и индексов `apartment_view`; Go-структуры фильтра с методами `ToSQL()` и `Match(apartment)`; фрагмент OpenAPI → TS-типы и конфиг фильтров для UI.
- «Нельзя сбилдить»: генератор падает на неподдержанной паре тип + оператор, а CI проверяет, что сгенерированные файлы актуальны (`git diff --exit-code`).
- `extractor_version` = хеш манифеста + промпта. После добавления поля фоновая задача переизвлекает только активные объявления, у остальных поле = «неизвестно».

### 2.7 Поиск

- Запросы идут только в `apartment_view`, все индексы частичные: `WHERE status = 'active'`. Активных квартир — десятки тысяч, так что ограничение по дате не нужно.
- Индексы: btree на `price_usd`, `rooms`, `district`; GIST на `geo`; `(last_event_at, id)` для ленты.
- Пагинация курсором `(last_event_at, id)`, без OFFSET.
- Радиус — `ST_DWithin(geo, point, meters)`.

### 2.8 Уведомления

- Событие кластера → задача `match_subscriptions`: проходим по всем активным `saved_search` и вызываем `Match()`. Это та же логика фильтра, что и в поиске, сгенерированная из манифеста. При нашем числе пользователей перебора хватает.
- На каждое совпадение — `INSERT INTO notification_log … ON CONFLICT DO NOTHING`. Строка вставилась — ставим задачу `send_telegram`. Так ретраи не дают дублей.
- Очередь `send_telegram` с ограниченным числом воркеров и бэкоффом на 429 — чтобы не упираться в лимиты Bot API.
- Снижение цены считается событием от 3%. «Снова сдаётся» — после 14 дней неактивности. Оба порога в конфиге.

### 2.9 Наблюдаемость

- Логи через `slog` в JSON.
- Расходы на LLM за день и по цели (извлечение / судья / эмбеддинги) считаются из `llm_call`, с дневным лимитом: при превышении извлечение ставится на паузу.
- На странице админа: сколько объявлений пришло из каждого источника, сколько отклонено и почему, сколько склеено и каким методом.

## 3. Будущие фичи

Всё, что обсудили, но отложили за MVP. Данные для первых трёх пунктов MVP уже собирает.

| Фича | Зачем | Что нужно |
| --- | --- | --- |
| Признак «агент» и фильтр «только собственники» | самая востребованная фича при местных комиссиях | порог по `contact.postings_count`, посмотреть на реальное распределение |
| Автосклейка по контакту + параметрам без LLM | меньше вызовов судьи | сверить правило с накопленными вердиктами LLM в `match_edge` |
| Подбор порогов и дешёвый классификатор по истории рёбер | судья нужен только в серой зоне | достаточно размеченных пар |
| Сравнение картинок (pHash / dHash, поиск по 4 частям по 16 бит) | сильный сигнал для кандидатов | скачивание фото; учесть общие фото подъезда у агентов и водяные знаки |
| Свои копии фото (Cloud Storage) | ссылки источников умирают вместе с объявлением | идёт вместе со сравнением картинок |
| Флаг подозрительно низкой цены | отсев приманок | медиана по району + комнатам из `apartment_view` |
| История прошлых сдач в карточке («сдавалась в мае за $X») | понятно, честная ли цена сейчас | UI поверх `price_point` и событий `relisted` |
| Посуточная аренда | отдельный сегмент рынка | снять отклонение по периоду, отдельный фильтр и, возможно, отдельная лента |
| Геокодинг адресов | карта и радиус для объявлений без координат | нормализация грузинских названий улиц и транслитерации |
| Поиск по нарисованной области и «рядом с метро» | удобнее фильтра по району | полигоны в PostGIS, справочник станций |
| Вход на сайт и управление подписками в веб-интерфейсе | удобнее редактировать фильтры | Telegram Login Widget, тот же `telegram_id` |
| Создание и редактирование поиска прямо в боте | можно обойтись без сайта | диалоги бота или Telegram Mini App |
| Дайджест раз в день вместо мгновенных уведомлений | для тех, кто не спешит | настройка в `saved_search` |
| Админка модерации кластеров | ручное разделение и слияние, разбор конфликтов | рёбра `method = manual` уже заложены |
| Ранжирование с учётом полноты | подробные объявления выше | сортировка «по релевантности» рядом с «по свежести» |
| Facebook-группы как источник | больше объявлений от собственников | сложный сбор, нет открытого API |
| Платные фичи, если дойдёт до денег | платят за скорость и объём, не за повторы | больше подписок, чаще обход любимых источников |
| Отдельное хранилище для чтения (Meilisearch / Elasticsearch) | если Postgres упрётся в скорость | заменить проектор `apartment_view`, сторона записи не меняется |
